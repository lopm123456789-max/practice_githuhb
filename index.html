연습허브

팀장·동료 요청을 웹 사이트, VS Code, 데스크톱 앱 방식으로 직접 처리해 보는 모의 연습장임. 세 모드는 같은 저장소를 공유하며 실제 GitHub와 연결되지 않음.

로컬 ↔ 원격 현황

요청 목록

    알림

    자주 묻는 질문 (실제로 물어본 내용 정리)

    Q1. 로컬에서 브랜치 자체를 push 할 수 있나?

    가능함. push는 브랜치 단위로 동작함. 원격에 없으면 같은 이름의 브랜치가 새로 생기고, 있으면 새 커밋만 올라감.

    git push -u origin 브랜치명처음 올릴 때 사용. -u로 연결하면 다음부터 git push만 입력해도 됨
    git push연결된 원격 브랜치로 새 커밋을 올림
    git push origin 로컬명:원격명다른 이름으로 올림 (예: test:main)
    git push --all origin모든 로컬 브랜치를 한 번에 올림
    git push origin --delete 브랜치명원격 브랜치 삭제 (로컬은 유지)
    • VS Code: 새 브랜치에서는 Publish Branch, 올린 뒤에는 동기화(↑숫자) 버튼
    • 데스크톱 앱: 처음 Publish branch, 이후 Push origin 버튼
    • 둘 다 내부적으로 git push -u origin 브랜치명과 같음

    Q2. 브랜치에서 수정한 걸 push하면 main에도 반영되나?

    반영되지 않음. 원격의 같은 이름 브랜치에만 올라가고 main은 그대로임.

    [내 컴퓨터]                      [원격 저장소]
feature/login 에서 수정·커밋
        │ git push
        ▼
                               feature/login  ← 여기에만 올라감
                               main           ← 변화 없음
    • main에 넣으려면: push → PR 생성 → 리뷰·승인 → Merge
    • 같은 브랜치에 계속 push 가능하며, 열려 있는 PR에 커밋이 자동으로 추가됨
    • 브랜치 작업이 망가져도 main은 안전함. 그래서 실무에선 main에 직접 올리지 않음

    Q3. push가 거절되는 경우는?

    • 원격에 내가 받지 않은 새 커밋이 있음 → 먼저 pull
    • 보호 규칙(PR 필수)이 걸린 브랜치에 직접 push → 새 브랜치에 올리고 PR
    • 쓰기 권한이 없음(403) → 협업자 초대를 받거나 Fork 후 PR

    Q4. 로컬 main에서 pull하면 원격의 다른 브랜치도 딸려오나?

    내용은 main에만 합쳐짐. 다른 브랜치는 정보(목록과 커밋)만 받아지고, 내 로컬 브랜치로 자동 생성되지 않음.

    git pull  =  git fetch  +  git merge
            (원격 정보 받기)   (지금 브랜치에만 합치기)

[pull 후 내 컴퓨터]
main              ← 원격 main 내용이 합쳐짐
origin/main       ← 원격 상태 기록
origin/feature-a  ← 다른 브랜치는 '기록'만 생김 (로컬 브랜치 아님)
    • 다른 브랜치에서 작업하려면 그 브랜치로 체크아웃함 → 그때 로컬 브랜치가 생김 (git switch feature-a)
    • git pull origin main 처럼 브랜치를 지정하면 main 정보만 받음
    • 다른 브랜치 내용이 main에 섞여 들어가는 일은 없음. main에 넣으려면 PR 머지가 필요함
    • 연습허브: VS Code 상태바 ⎇ 메뉴, 데스크톱 앱 Current branch 메뉴에서 'origin/이름'으로 보이는 것이 이것임

    Q5. 실무에선 어떤 순서로 작업하나? (로컬 main 경유 vs 원격 main 직행)

    둘 다 아님. 브랜치는 같은 이름의 원격 브랜치로 올리고, main에는 PR 머지로만 합치는 방식이 표준임 (GitHub Flow).

    ① git switch -c feature/x        로컬에서 브랜치 만들기
② 수정 → 커밋 (여러 번 가능)
③ git push -u origin feature/x   원격의 같은 이름 브랜치로 올리기
④ 웹에서 PR 생성 (feature/x → main) → 리뷰 → Merge
⑤ git switch main → git pull      로컬 main 최신화
⑥ 다 쓴 브랜치 삭제 (원격·로컬)
    방식평가
    로컬 main에 merge → 원격 main push리뷰 없이 main이 바뀜. 보호된 main이면 거절됨. 혼자 하는 저장소에서만 가끔 씀
    git push origin feature/x:main가장 위험함. 리뷰·기록 없이 원격 main을 직접 덮어씀. 권장하지 않음
    브랜치 push → PR → 머지권장. 리뷰·토론·자동 검사·이슈 연결이 남고 main이 늘 안정적임
    • 정리: 원격 브랜치에 push → 거기서 PR로 main에 머지가 정답임. 원격 브랜치에서 main으로 옮기는 단계는 push가 아니라 웹의 PR Merge 버튼으로 함
    • 참고: 로컬 main으로 옮기는 동작은 push가 아니라 merge임. push는 항상 '내 컴퓨터 → 원격' 방향임
    • 혼자 쓰는 연습 저장소라도 이 순서로 하면 실무 습관이 그대로 잡힘

    Q6. 로컬과 원격은 어떻게 구분하나?

    로컬 = 내 컴퓨터의 저장소(VS Code·데스크톱 앱으로 작업). 원격 = GitHub에 있는 저장소(웹 사이트, 이름은 보통 origin). 둘은 push·pull 할 때만 맞춰짐.

    표기뜻
    main로컬 main 브랜치
    origin/main원격 main 브랜치 (마지막으로 확인한 상태)
    [로컬]커밋·브랜치 생성·스테이징 등. 원격엔 아무 변화 없음
    [로컬→원격]push / Publish: 내 커밋을 GitHub로 올림
    [원격→로컬]clone / pull / fetch: GitHub 내용을 내 컴퓨터로 받음
    [원격]PR·리뷰·머지·이슈·보호 규칙 등 웹에서만 하는 일
    • 연습허브 왼쪽 '로컬 ↔ 원격 현황' 표에서 브랜치별로 어디에 있는지, 몇 개를 올리고 받아야 하는지 볼 수 있음
    • ↑숫자 = 로컬에만 있는 커밋(push 필요), ↓숫자 = 원격에만 있는 커밋(pull 필요)
    • 합치는 곳도 구분함: 로컬 main 에 합치기 = merge (VS Code: 분기 병합 / 데스크톱: Merge into current branch). 원격 main 에 합치기 = PR 머지 (웹). PR은 원격에만 있음

    Q7. 컨플릭트(충돌)는 언제 나고 어떻게 푸나?

    같은 파일의 같은 줄을 양쪽이 다르게 고쳤을 때 남. 다른 파일이나 다른 줄이면 자동으로 합쳐짐.

    <<<<<<< main (현재 변경: 내 쪽)
알림 시간=10:00
=======
알림 시간=08:30
>>>>>>> feature/c-alarm (수신 변경: 들어오는 쪽)
    상황위치해결 순서
    로컬 브랜치끼리 merge로컬충돌 정리 → 스테이징 → 커밋 (원격 반영은 push)
    push 거절 후 pull원격→로컬pull → 충돌 정리 → 커밋 → push
    PR 충돌 (간단)원격웹 Resolve conflicts → Commit merge → PR 머지
    PR 충돌 (복잡)로컬→원격로컬 head 브랜치에 origin/main merge → 정리 → 커밋 → push
    해결이 어려울 때로컬병합 중단(git merge --abort) → 상의 후 다시
    • VS Code: 충돌 부분 위에 [현재 변경 수락 / 수신 변경 수락 / 두 변경 모두 수락] 버튼이 뜸
    • 데스크톱 앱: 충돌 창에서 파일별로 편집기 열기·한쪽 선택 후 [Continue merge]
    • 예방: 작업 전 pull, 브랜치는 작게 자주 머지, 같은 파일을 여럿이 동시에 고칠 땐 미리 말하기
    • 연습: 왼쪽 [컨플릭트 실습] 트랙

    Q8. 다른 사람 저장소에 올려도 되나?

    허락 없이 올리면 안 됨. 권한이 없으면 403으로 막히고, 권한이 있더라도 소유자와 협의가 먼저임. 내 작업은 내 저장소에 두고, 기여하고 싶으면 Fork 후 PR을 보내는 것이 원칙임.

    Q9. 데스크톱 앱에 'Push origin' 안내가 뜨면 꼭 눌러야 하나?

    꼭 지금 할 필요는 없음. 커밋은 했지만 아직 로컬에만 있다는 뜻임 (현황표의 ↑숫자). 누르지 않아도 커밋은 사라지지 않지만, 내 컴퓨터에만 있어 동료가 못 보고 백업도 안 됨.

    확인할 것눌러도 됨잠깐 멈춤
    Current branch내 작업 브랜치 (feature/…)팀 저장소의 main
    History 탭 커밋올리려고 만든 커밋연습·실수 커밋, 로컬에만 두기로 한 merge
    저장소 주인내 저장소다른 사람 저장소 (403 거절)
    • 팀 저장소 main 에 커밋했다면: New branch 로 새 브랜치를 만들어 커밋을 옮긴 뒤 Publish → PR
    • Ctrl + P = Push origin 단축키
    • 이 안내를 안 보고 싶다면: 끄는 설정은 없음. ① push 해서 올리거나 ② 필요 없는 커밋이면 History 의 Undo(커밋 취소) → Changes 의 Discard(변경 버리기)로 원격과 같게 만들면 사라짐. ③ 다른 브랜치로 옮기면 그 브랜치 기준으로 다시 표시됨
    • 주의: 이미 push 한 커밋은 Undo 가 안 됨. 그때는 되돌리는 새 커밋(revert)을 만들어 push 함

    Q10. 팀이 바뀌어 다른 팀원 코드·새 저장소로 바꾸려면? (파일 이름은 같음)

    새 저장소를 새 폴더로 클론하는 것이 가장 안전함. 예전 폴더는 확인 후 보관하거나 지움.

    도구방법
    데스크톱 앱File → Clone repository → 새 저장소 선택 → Local path 를 기존과 다른 폴더로
    VS CodeCtrl+Shift+P → Git: Clone → 새 주소 → 새 폴더
    명령어git clone 새주소 새폴더이름
    • 하지 말 것: 예전 파일을 새 폴더에 복사해 덮기 (이름이 같아 팀원 코드가 내 옛 코드로 바뀜), 예전 폴더에서 새 저장소 pull (unrelated histories), 예전 코드를 새 저장소에 push
    • 예전 폴더를 계속 쓰려면 (고급): git branch backup-old → git remote set-url origin 새주소 → git fetch origin → git switch -C main origin/main
    • 옛 작업 중 살릴 것은 새 저장소에서 브랜치를 따 손으로 옮겨 PR

    Q11. CRLF 와 LF 는 뭐고 왜 문제가 되나?

    줄 끝 표시 방식임. CRLF(\r\n) = 윈도우, LF(\n) = 맥·리눅스·서버. 편집기가 줄바꿈을 바꿔 저장하면 눈에는 같아도 Git 은 모든 줄이 바뀐 것으로 봄.

    증상해결
    한 줄 고쳤는데 파일 전체 diff편집기에서 LF 로 저장 (VS Code 상태바 CRLF/LF 클릭)
    warning: LF will be replaced by CRLF경고일 뿐 파일은 안전함. 팀 설정을 맞추면 사라짐
    팀원마다 줄바꿈이 다름저장소에 .gitattributes 추가: * text=auto (모두에게 적용)
    윈도우 개인 설정git config --global core.autocrlf true
    • 데스크톱 앱 diff 에 '줄바꿈 변경' 경고가 뜨면 이 문제임. 연습허브 diff 의 ␍ 표시가 윈도우 줄바꿈 문자임

    Q12. 특정 파일만 올리려면?

    push 는 커밋 단위라 파일을 고르는 단계가 없음. 커밋할 때 올릴 파일만 골라야 함.

    도구방법
    VS Code올릴 파일만 + (스테이징) → 커밋 → push. ⚠ 아무것도 스테이징 안 하고 커밋하면 전부 커밋됨
    데스크톱 앱Changes 에서 올릴 파일만 체크 → Commit → Push
    명령어git add 파일명 → git commit -m "메시지" → git push
    항상 제외할 파일.gitignore 에 적기 (예: .env, *.log, node_modules/)
    • 고르지 않은 파일은 커밋 안 된 채 내 컴퓨터에 남음 (지워지지 않음)
    • 이미 커밋된 파일은 .gitignore 에 적어도 계속 추적됨 → 처음부터 넣는 게 중요. 비밀 키가 올라갔다면 키부터 교체

    Q13. Accept Current Change 와 Incoming Change 가 헷갈림

    기준은 하나임: 지금 체크아웃해 있는 브랜치 = Current(현재 변경), 합쳐 들어오는 쪽 = Incoming(수신 변경).

    <<<<<<< HEAD (Current Change)          ← 지금 내 브랜치 내용
기한: 10월 24일
=======
기한: 10월 31일
>>>>>>> origin/main (Incoming Change)  ← 들어오는 쪽 내용
    상황Current (위)Incoming (아래)
    main 에서 feature 를 mergemainfeature
    내 브랜치에서 pull내 로컬 커밋원격 (동료가 올린 것)
    내 브랜치에 origin/main merge내 브랜치main
    ⚠ rebase 중main (기준)내 커밋 ← 반대
    • 요령: ① 표시 줄 뒤 브랜치 이름 확인 ② 상태바에서 지금 브랜치 확인 ③ 둘 다 필요하면 Accept Both 후 손질
    • 연습: 컨플릭트 실습 '누구 것을 남길까', VS Code·데스크톱 실전 요청

    Q14. "Unable to pull when changes are present on your branch … would be overwritten" 오류

    커밋 안 한 내 수정과 원격 변경이 같은 파일이라, pull 하면 내 수정이 덮일 수 있어 Git 이 막은 것임. 고장이 아님.

    내 수정이…데스크톱 앱VS Code명령어
    살릴 작업Commit → Pull origin → (충돌 시 해결) → Push+ → ✓ 커밋 → 끌어오기git commit → git pull
    아직 이른 작업Branch → Stash all changes → Pull → Stashed Changes [Restore]··· → 임시 저장 → 끌어오기 → 임시 저장 꺼내기git stash → git pull → git stash pop
    버릴 실험파일 우클릭 → Discard changes → Pull↶ 변경 내용 취소 → 끌어오기git restore 파일 → git pull
    • 잘 모르겠으면 Stash 가 가장 안전함 (수정이 따로 보관됨)
    • Restore(pop) 때 같은 줄이 바뀌었다면 충돌 표시가 생김 → Current(받은 내용) / Incoming(내 임시 저장) 중 골라 정리
    • 겹치지 않는 파일만 고쳤다면 이 오류 없이 Pull 됨

    Q15. Fork 와 저장소 간 PR 은 어떻게 하나?

    쓰기 권한이 없는 저장소(원본)에 기여할 때 쓰는 방법임. Fork = 원본을 내 GitHub 계정으로 복사(원격끼리), Clone = 내 컴퓨터로 복사.

    원본 kim-team/team-tool  ──Fork──▶  내 fork jeonnam-dev/team-tool  ──Clone──▶  내 컴퓨터
        ▲                                     ▲   (origin)                        │
        └──── PR (base 원본:main ← 내fork:브랜치) ─┴──── push ◀──────────────────────┘
원본이 바뀌면: 웹 [Sync fork]  또는  로컬 upstream/main merge → push
    단계방법
    Fork원본 저장소 오른쪽 위 [Fork]
    Clone내 fork 주소로 클론 (origin = 내 fork, upstream = 원본)
    작업·push브랜치 → 커밋 → 내 fork(origin)에 push
    PR내 fork 의 [Contribute → Open pull request] 또는 원본 New pull request → compare across forks
    동기화내 fork 웹 [Sync fork] → 로컬 Pull. 또는 git fetch upstream → git merge upstream/main → git push
    특정 브랜치만git switch -c dev upstream/release/v1 → git push -u origin dev
    • 원본에 직접 push 하면 403 으로 거절됨 → 항상 내 fork 로 push
    • 머지는 원본 관리자가 함. PR 이 열려 있는 동안 내 fork 브랜치에 push 하면 PR 에 자동으로 붙음
    • 연습: 왼쪽 [Fork 실습] 트랙

    Q16. 남의 저장소가 GitHub Desktop 클론 목록에 안 보임

    Clone repository 의 GitHub.com 탭은 내 계정이 소유하거나 Collaborator·조직 멤버인 저장소만 보여 줌. 남의 저장소는 원래 안 나옴.

    상황해결
    공개 저장소[파일] → Clone repository → URL 탭 → 주소(https://github.com/소유자/저장소) 또는 소유자/저장소 입력 → Clone
    비공개 저장소소유자에게 Collaborator 초대 요청 → 메일·github.com/notifications 에서 초대 수락 → 목록에 나옴 (수락 전엔 Repository not found)
    조직 저장소조직 멤버 확인, 조직이 앱 접근을 막았으면 Settings → Applications 에서 GitHub Desktop 접근 요청
    방금 초대 수락함목록 오른쪽 새로고침 버튼 또는 앱 재로그인
    • 클론은 읽기용임. push 하려면 Collaborator 권한, 권한이 없으면 Fork 후 PR
    • VS Code 는 목록 없이 Git: Clone 에 주소를 바로 넣음

    Q17. 현업 이슈 관리: 할당·마감·우선순위·커밋 연결·위키

    버그 발생 → 이슈(템플릿) → 담당자·라벨·마일스톤 → 보드(Status·Priority·Due)
        → 이슈에서 Create a branch → 커밋 "… #번호" (참조) → PR "Fixes #번호" → main 머지
        → 이슈 자동 Closed → 보드 자동 Done → 위키에 장애 기록 (이슈·커밋·코드 permalink 링크)
    하고 싶은 것GitHub 기능위치
    담당자 지정Assignees이슈 오른쪽
    마감일Milestone(Due date) · 보드의 Due 칸Issues → Milestones / Projects
    우선순위·진행 상태Projects 의 Priority·Status 칸Projects 탭 (Board·Table)
    양식 통일이슈 템플릿 (.github/ISSUE_TEMPLATE)Settings → Features → Set up templates
    작업 브랜치 연결Development → Create a branch이슈 오른쪽
    커밋 ↔ 이슈 연결메시지에 #번호 (참조) / Fixes·Closes #번호 (main 들어가면 닫힘)커밋 메시지·PR 본문
    보드 자동 이동Workflows: Item closed·PR merged → Done (기본 켜짐)Projects → Workflows
    코드 줄 공유Permalink (커밋 SHA 고정 주소)파일 줄 번호 클릭 → Copy permalink
    지식 기록Wiki (별도 저장소 repo.wiki.git)Wiki 탭
    내 일만 보기검색 is:open assignee:@meIssues 검색창
    • 요령: 이슈 1건 = 브랜치 1개 = PR 1개, PR 본문에 Fixes #번호 를 쓰는 습관
    • 그 밖에 현업에서 많이 씀: PR 템플릿, CODEOWNERS(파일별 자동 리뷰어), GitHub Actions(자동 테스트), Discussions(질의응답)

    Q18. 현업 PR 협업 기능 (템플릿·Draft·CODEOWNERS·CI·제안·자동 머지)

    기능하는 일만드는 곳
    PR 템플릿새 PR 본문을 양식으로 자동 채움main 의 .github/pull_request_template.md
    Draft PR작업 중 표시. 머지 불가, 코드 소유자 리뷰 요청 보류Create draft pull request → 끝나면 Ready for review
    CODEOWNERS파일 경로별 담당 리뷰어를 자동 요청.github/CODEOWNERS (예: *.py @김주무관), base 브랜치에 있어야 함
    CI 체크 (Actions)PR 마다 자동 검사, ✓/✕ 표시.github/workflows/*.yml · Actions 탭
    필수 규칙코드 소유자 승인·체크 통과 없이는 머지 불가Settings → Branches → Require review from Code Owners / Require status checks
    Suggested changes리뷰어가 고칠 코드를 직접 제안, 작성자가 버튼으로 커밋PR Conversation → Commit suggestion / Add to batch
    Auto-merge조건이 채워지면 자동 머지Settings → Allow auto-merge → PR 의 Enable auto-merge
    • CODEOWNERS 파일만으로는 머지를 막지 못함 → 보호 규칙에서 Require review from Code Owners 를 켜야 함
    • 소유자는 쓰기 권한이 있어야 하고, 마지막에 일치한 줄이 우선함
    • 제안을 반영하면 제안한 사람이 공동 작성자(Co-authored-by)로 남음
